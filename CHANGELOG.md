# Changelog

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — [SemVer](https://semver.org/lang/ru/).

## [2.1.1] — 2026-07-30

Патч по итогам контрольной перепроверки 2.1.0. Поведение выданных прав
не меняется.

### Исправлено

- **`clusters.auth_path = ""` молча подменялся дефолтом**: `coalesce()`
  в Terraform пропускает пустые строки так же, как null, — конфиг выглядел
  применённым не так, как написан. Теперь auth_path — либо null (дефолт
  `kubernetes/<ключ>`), либо непустой путь без слэшей по краям и без `//`;
  раньше `"/x"` доживал до apply.
- `jwt_path` / `approle_path`: запрещён `//` (края и пустота запрещены с 2.1.0).

### Документация

- «Снять объект с управления»: описан демонтаж AppRole. `approle_roles = {}`
  при `manage_approle_backend = true` — это destroy бэкенда, и с 2.1.0 он
  упирается в `prevent_destroy`; рецепт — `state rm`, затем пустая карта,
  затем `vault auth disable` руками. Там же — что полный снос вызова модуля
  требует предварительного `state rm` защищённых ресурсов.

## [2.1.0] — 2026-07-30

По итогам повторного аудита (шесть ревьюеров + адверсариальная верификация,
спорное проверялось на живом Vault 2.0.3). Тема прежняя: молчаливый отказ
должен быть ошибкой plan.

### Безопасность

- **Закрыт обход `allow_destroy = false` через metadata.** `write_paths` в KV v2
  выдавал `create`/`update` на `metadata/…`, а этого хватает на
  `vault kv metadata put -max-versions=1` — следующая запись безвозвратно
  вытесняла всю историю секрета (проверено на живом Vault: версии исчезают из
  metadata целиком, не возвращает даже root). Теперь писатель получает на
  `metadata/…` только `read, list`; запись туда — по `allow_destroy = true`
  либо точечно через `raw_path_capabilities`. **Это сужение уже выданных
  прав** — см. README «Обновление с 2.0.0 на 2.1.0».
- **deny, смешанный с другими правами на одном пути, валит plan.** Слияние
  правил по путям превращало `read_paths` + `path_capabilities = { путь =
  ["deny"] }` в строфу `["read", "deny"]`, а deny в Vault побеждает всё —
  добавленное право молча не работало. Одиночный deny на своём пути легален.

### Исправлено

- **`token_period = 0` ложно валил plan** во всех трёх типах ролей (регрессия
  проверки из 2.0.0): ноль — «не периодический», как его понимает провайдер,
  а не период в ноль секунд.
- **`manage_jwt_backend` / `manage_approle_backend` true → false тихо уничтожали
  бэкенд в Vault со всеми ролями под ним** («1 destroyed» в выводе, роли в
  state, логин сломан у всех). На оба бэкенда поставлен `prevent_destroy` —
  по образцу KV-маунта; порядок штатного отключения — README «Снять объект
  с управления» (`terraform state rm`, потом флаг).
- **`jwt_validation_pubkeys` из `file()` давали вечный diff**: `file()`
  оставляет хвостовой перевод строки, Vault хранит PEM без него. Ключи
  обрезаются `trimspace`.
- **Роль на несуществующий кластер** показывала рядом с внятным precondition
  сырой `Invalid index` из outputs — лишняя ошибка убрана (`try()`).
- **Шапка «Маунты: …»** больше не приписывает политике kv_mount, если политика
  его не трогает (raw-only / extra_rules-only).

### Валидации (всё — ошибки plan, раньше молча или падало на apply)

- пустой список прав в `path_capabilities` / `raw_path_capabilities` /
  `mounts[*].path_capabilities` — давал строфу `capabilities = []`, Vault
  принимает, прав ноль; дыра в проверке 2.0.0 (`alltrue` по пустому — true);
- элементы `*_paths` и ключи `*_capabilities`: пустые, со слэшами по краям,
  с `//` — политика с таким путём применяется и молча не матчит; то же для
  `//` в `kv_mount` / `mounts[*].mount` (Vault нормализует путь маунта,
  политика остаётся как написана);
- пустые ключи карт (`policies`, `services`, `jwt_roles`, `raw_policies`,
  `approle_roles`, `clusters`, `k8s_roles`) — apply падал посреди прогона
  с криптичным 405;
- отрицательные TTL / `token_period` / `secret_id_ttl` / `secret_id_num_uses`;
  пустой `user_claim`; пустые или со слэшами по краям `jwt_path` /
  `approle_path`; `default_lease_ttl` / `max_lease_ttl` кластера не
  Go-длительность.

### Добавлено

- Права `subscribe` и `recover` в белом списке capabilities — Vault их
  принимает (проверено на 2.0.3), модуль отвергал. Белый список теперь один
  на модуль (`local.valid_capabilities`) вместо шести копий.
- Тестов 43 → 64: фикстура `policy_files_dir` (рендер файловых политик,
  `data_prefix`, экранирование `$$`), extra_rules-политика, deny-конфликт
  и одиночный deny, пустые списки прав, кривые пути, пустые ключи,
  `token_period = 0`, trimspace pubkeys, metadata-сужение — плюс закрыта
  мутационная дыра: ветка `token_explicit_max_ttl` периодического guard'а
  не ловилась ни одним тестом.
- CI: `terraform plan` каждого примера с фиктивными значениями — `validate`
  не вычисляет validation/precondition, и сломанный пример проходил зелёным
  (так в 1.7.0 уехал нерабочий AppRole).

### Документация

- Убрано неверное «из двух строф на один путь Vault оставляет последнюю» —
  на живом Vault 2.0.3 строфы объединяются; слияние модуля ценно
  детерминизмом, а не защитой от last-wins.
- `policy_files_dir` читает только верхний уровень каталога — теперь это
  сказано явно (подкаталоги молча игнорируются).
- Разделы «Снять объект с управления» и «Обновление с 2.0.0 на 2.1.0»;
  пример с двумя `bound_claims` разбит на два блока (единый был невалидным
  HCL при копипасте); «`jwt_backend` задаёт больше одного способа» уточнено
  до «не ровно один» — ноль способов тоже ошибка.

## [2.0.0] — 2026-07-29

Ревизия по итогам аудита. Общая тема релиза: всё, что раньше молча давало
неработающую политику или роль, теперь валит `plan`.

Адреса ресурсов не изменились — `moved`-блоки и импорт не нужны. Порядок
обновления и таблица «было/стало» — в README, раздел «Обновление с 1.x на 2.0».

### Требования

- **Нижняя граница Terraform поднята с `>= 1.5` до `>= 1.12`.** До 1.12
  Terraform вычислял оба операнда `||`, поэтому проверка входов
  `m.kv_version == null || contains([1, 2], m.kv_version)` доводила `null` до
  `contains`, а тот `null` не принимает. Срабатывало на маунте без явно
  заданной версии — то есть на самом обычном случае. Границу нашёл прогон
  тестов по версиям: 1.9.8, 1.10.5 и 1.11.4 валятся, 1.12.0 проходит.

### Исправлено

- **AppRole был нерабочим целиком.** `auth_approle.tf` читал `token_period` и
  `token_no_default_policy`, которых не было в типе `approle_roles`, — любой
  конфиг с непустым `approle_roles` падал на `plan` с `Unsupported attribute`,
  включая собственный `examples/minimal`. Оба поля добавлены в переменную.
  `terraform validate` этот класс ошибок не ловит: Terraform не типизирует
  `each.value` статически.
- **Опечатка в capability молча обесточивала правило.** Валидация набора прав
  стояла только на верхнеуровневом `policies`; неизвестное право в
  `services.path_capabilities`, `*.raw_path_capabilities` и
  `mounts[*].path_capabilities` выпадало при сборке правил, оставляя строфу
  `capabilities = []` — Vault такую принимает, прав она не даёт. Проверка
  распространена на все поля обоих входов.
- **`mounts[*].kv_version` не проверялся** и при любом значении кроме `2`
  молча раскрывался как v1 — то есть без префикса `data/`.
- **Коллизии имён только предупреждали.** `check`-блоки в Terraform не
  останавливают `apply`: одно имя политики в двух источниках давало `Warning`,
  после чего `merge()` оставлял последний источник, а остальные определения
  терялись. Оба `check` заменены на `precondition`.
- **Проверки TTL были только у JWT-ролей.** `token_ttl` больше
  `token_explicit_max_ttl` и `token_period` вместе с ненулевым потолком теперь
  валят `plan` и для kubernetes-, и для AppRole-ролей.
- **`write_paths` в KV v2 не давал обычный `vault kv delete <path>`.** Без
  `-versions` CLI шлёт `DELETE` на `data/<path>`, а модуль выдавал на `data/`
  только `create, read, update, patch`; право `update` на `delete/<path>`
  покрывает лишь форму с явной версией. Самая обычная команда удаления
  отвечала 403 тому, у кого «есть запись». На `data/` добавлен `delete`.
  Проверено на живом Vault, что это по-прежнему мягкое удаление: секрет
  скрывается, `undelete` возвращает прежнее значение, `destroy` без
  `allow_destroy` остаётся запрещённым.
- **Периодический токен прижимался `token_max_ttl`, и это не проверялось.**
  Проверка была только на `token_explicit_max_ttl`. На живом Vault роль с
  `period = 86400` и `token_max_ttl = 900` выдаёт `ttl = 899`, и `renew` его не
  поднимает — период задавлен полностью. Теперь `token_period` требует нуля
  в обоих полях, у всех трёх типов ролей.
- **Политика без единой `path`-строфы проходила проверку.** `precondition`
  смотрел на `trimspace(policy) != ""`, а у сгенерированной политики всегда
  есть шапка-комментарий, поэтому «пустой» она не бывала никогда — проверка
  ловила только `raw_policies` и файловые. Теперь считаются `path`-строфы.
- **`kv_mount = ""` и `mounts[*].mount = ""` проходили валидацию:** пустая
  строка не содержит слэшей, а проверялись только они. Пути вырождались
  в `/data/…` — Vault такую политику принимает и не матчит.

### Добавлено

- `manage_approle_backend` (по умолчанию `true`) — раньше AppRole-бэкенд
  создавался безусловно, и его нельзя было отдать под уже существующий маунт
  иначе как через импорт. Дефолт `true`, а не `false` как у `manage_kv_mount`
  и `manage_jwt_backend`, — чтобы обновление не снесло бэкенд вместе с ролями.
- `tests/` — 43 прогона `terraform test` без живого Vault (`command = plan`):
  раскладка путей v1/v2, `allow_destroy`, слияние пересекающихся путей,
  `raw_path_capabilities`, микс маунтов, все `validation` и `precondition`.
- `LICENSE` (MIT), `CHANGELOG.md`, CI на GitHub Actions (`fmt`, `validate`,
  `test`, `validate` каждого примера). Тесты гоняются матрицей по двум
  версиям — `1.12.0` (объявленная нижняя граница) и `latest`. Прогон на
  границе здесь не формальность: расхождение в вычислении `||` между 1.11
  и 1.12 ловится только так.
- Строка `vault_auth_backend.approle[0]` в таблице импорта.

### Изменено

- `vault_approle_auth_backend_role.backend` берётся из `var.approle_path`, а не
  из `vault_auth_backend.approle[0].path` (иначе при `manage_approle_backend =
  false` ссылки не на что разрешать). Зависимость сохранена через `depends_on`.
- `output "approle_login_path"` по той же причине больше не зависит от ресурса
  бэкенда.
- README: убрано упоминание `check`, снятого ещё в 1.x (пересечение
  `read_paths`/`write_paths` намеренно разрешено); «три источника политик» →
  четыре, `services` тоже их порождает; поправлено число примеров.

### Убрано

- `examples/*/.terraform.lock.hcl` — были закоммичены с единственным хешем
  `h1:` под `linux_amd64`, из-за чего `terraform init` в примере падал на
  несоответствии контрольных сумм у всех, кто не на Linux/amd64.
- Мёртвое правило `!*.example` в `.gitignore`: под `terraform.tfvars` (точное
  имя) и `*.auto.tfvars` (суффикс) файлы `*.example` и так не попадали.
